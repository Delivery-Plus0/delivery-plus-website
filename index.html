      Built for Egypt

      Arabic first, right to left, priced in pounds

      Arabic is the default language unless the phone is set to English, and every screen mirrors for right-to-left reading. Prices are Egyptian pounds and phone numbers are Egyptian mobiles, normalized to +20.

      • Translated notifications. The backend sends a message key and its values, so each person reads an alert in their own language.
      • Words kept as written. A restaurant's rejection reason sits inside the Arabic sentence in the words the restaurant used.
      • Checked on every change. A test fails if any text in an app is missing its Arabic translation.

      Under the hood

      Twelve services, one source of truth

      The apps only ever talk to the API gateway. Behind it, each service owns its own data, and state changes travel between services as Kafka events.

      Automatic dispatch

      When the kitchen marks an order ready, the delivery service creates the delivery and claims a free driver in one compare-and-set write. Two orders can never take the same driver, and orders wait and retry until someone comes online.

      Events that can't get lost

      An order change and its event are written in the same database transaction (transactional outbox). Event ids are deterministic, every consumer skips what it already handled, and failures go to a dead-letter topic that can be replayed.

      Live tracking you can trust

      The customer's map updates over Server-Sent Events and falls back to polling. A driver's position only counts for their own current delivery, and the screen never says "Live" for old data.

      Money you can audit

      A flat EGP 25 delivery fee is split 50/50 and frozen on each order. Driver earnings go to an append-only ledger and settle after 12 hours. Refunds are full, once per payment, under a row lock, with an audit record.

      Checkout that can't overcharge

      At checkout the cart is checked again against the menu. If a price changed or an item sold out, the order is refused with what changed and the cart is updated, so nobody pays a price they didn't see.

      Safe by default

      Roles live in the JWT, every service checks ownership, and internal routes need signed requests. Phone codes are stored only as hashes, with attempt limits and cooldowns.

      Tested the way people use it

      Each app has its own UI test suite, written in Maestro and run in CI. The flagship test drives all three apps through one order: the customer orders, the restaurant app cooks it, the driver app delivers it, and the customer rates the driver.

      Every backend pull request also has to pass:

      • Unit tests and lint in every service
      • A full-stack run of the critical workflow
      • Migrations on a fresh database
      • CodeQL, dependency audit and container scans

      Honest status

      What works today, and what doesn't yet

      Working end to end

      • Ordering, kitchen workflow, automatic dispatch and delivery
      • Live tracking, ratings, order history and alerts
      • Delivery fee, driver earnings ledger and wallet
      • Cancellations with automatic full refunds
      • Menu editing with photos, profile photos
      • Arabic and English with right-to-left layouts

      Not there yet

      • Payments and refunds are simulated: no payment gateway yet
      • No SMS provider, so phone verification is off in production
      • No push notifications and no arrival-time estimate
      • No bank payouts for drivers
      • Production operations (metrics, backups, deploys) in progress
      • Screens are web builds; native Android and iOS are not yet tested
